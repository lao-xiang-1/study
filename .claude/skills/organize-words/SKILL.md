# organize-words — 单词词块整理

把有道单词本中**最新一批新增单词**整理成词块卡片：按同族词、近义词、反义词等把相关
单词归到同一组。（可把新词并入现有词块、不写 Anki SR 标记、绝不补充词表外单词）**先出
草稿供用户筛选，确认后才改词块笔记**，并由 git 兜底可回退。词块笔记与草稿的位置由
skill 目录下的 `config.json` 指定（见步骤 0），格式以该笔记为准。

## 必须遵守的规则

1. **先 git 前置检查**：动词块笔记前，先用 git 确认它处于干净已提交状态
   （见步骤 0）。若未跟踪或有未提交改动，**停下告诉用户处理**，不要继续。
2. **只整理最新一批**：只处理 `prepare.py` 输出的 `words`（即 `words.txt` 中最后一个
   `===日期===` 批次里、尚未出现在词块笔记中的单词）。
3. **先草稿后修改**：把全部建议方案写入 `{draft_path}` 供用户筛选。草稿**只列
   词族成员与一句理由**，不写释义/例句（确认后再补全）。**用户确认前不改词块笔记**。
4. **相关性门槛：宁缺毋滥**（最重要的一条）。只有当一组词满足下面三种关系之一时才建组：
   - **同族词**：同一词根的派生/屈折形式（`erode / erosion`、`succession / successor / successive`）；
   - **严格近义或反义**：互为「同一概念的不同说法」，或明确对立
     （`confess / concede / acknowledge`、`natural / synthetic`）；
   - **同一封闭范畴的并列成员**：同一种东西的不同实例，彼此互斥且可枚举
     （`semicolon / comma / asterisk` 标点符号、`spine / liver / lap` 身体部位、
     `singular / plural / dual` 语法中的数、`phase / session / spell` 都表「一段时间」）。

   以下都**不算**强相关，一律不建组：
   - 只是「同一领域的不同概念」的术语清单（`stack / thread / grid / overlay`、
     `coefficient / entropy / outlier / baseline`、`algebra / arithmetic / multiplication`）；
   - 靠形式归类的组：短语组（`play out / end up / set off`）、连字符复合词
     （`heads-up / well-being / single-handedly`）、同词性组（`merely / significantly / namely`）；
   - 宽泛的褒贬/情绪标签（`generous / cordial / decent / favorable`、`gloomy / miserable / pathetic`）；
   - 任何只能靠「都属于 X 领域」「都是负面词」这类泛泛理由成立的组。

   写每个组前自问：**能否用一句话说清这组词的共同点，且这句话不是「都属于某领域」？**
   说不清就删掉这组。**覆盖率不是目标**——本次有多少词没成组完全无所谓，它们下次运行还会出现。
5. **只用本批真实单词成组，绝不补充词**：分组只用本批单词（或并入现有组）。**绝不**补充
   词表外的词——`word / (补充词)` 这种形式（如 `ambiguous / (explicit)`）**永不可出现**。
   新增组（A 类）**至少 3 词**（建议 3–4 词，最多 5 词），不创建 2 词组；并入现有组（B 类）
   可只加 1 个词。
6. **组内成员必须同质**：宁可 3 词精准，也不要为了多覆盖一个词而塞入语义偏远的成员。
   例如「标点符号」组只放 `semicolon / comma / asterisk`，不要塞 `handwriting`；
   「行走不稳」组只放 `stumble / stagger / limp`，不要塞 `slip`、`reel`。
7. **绝不写 SR 标记**：不要输出任何 `<!--SR:...-->` 行——它们由 Anki/FSRS 自动生成与维护。
8. **允许修改现有词块，但仅限「把新词并入现有组」，且仅限真同族**：只有当新词与现有组是
   同一词根的派生/屈折（如 `precede` → `precedent / precedence / unprecedented`）才并入。
   松散的近义关系**不足以**改现有组（如 `somewhat` 之于 `slightly`、`catalyze` 之于
   `stimulate`——这类不要并入）。并入时在该组标题加入新词、并在其 `<!--SR:...-->` **之前**
   插入一个新小节 `### N. 新词`。**不得**删除、重排、改写已有小节或 SR 标记。
9. **续接编号**：新增组从 `prepare.py` 的 `next_group_number_cn` 起按选中项的顺序连续编号
   （三十七、三十八……），用中文数字。并入现有组不占新编号。
10. **释义精简**：`prepare.py` 的 `definition` **已经是精简好的「词性 + 主要义项」**——它已剥离
   【名】人名等噪音行、`<英>`/`<旧>` 等语域标签与括号补充说明，每个词性最多留 2 个义项、
   总长 ≤80 字。阶段二**直接采用**，必要时按卡片风格微调（如 `n. 意图，目的；adj. 专心的，专注的`）。
   **不要**再去 `words.csv` 取长释义重新精简。
11. **例句**：每词 2 个，英文句中目标词用 `**加粗**`，句末接全角括号中文翻译：
   `She was **intent** on finishing it.（她专心致志要完成它。）`（此步在阶段二生成正文时执行。）

## 工作流（分两阶段）

### 阶段一：生成草稿供筛选

#### 0. 读路径配置 + git 前置检查

先 Read `.claude/skills/organize-words/config.json`：

- `notes_path` —— 词块笔记，**相对项目根**（本仓库为 `lexical-chunk.md`）
- `draft_name` —— 草稿文件名，草稿固定放在 skill 目录内（本仓库为 `lexical-chunk-draft.md`）

草稿路径 = `.claude/skills/organize-words/` + `draft_name`。**后文涉及词块笔记的路径一律用
`notes_path`**，不要假设它叫 `lexical-chunk.md`、也不要假设它在项目根 —— 换个项目它可能
在 `English/` 之类的子目录下。

```bash
git status --porcelain -- {notes_path}
```
- 输出为空 → 工作区干净，继续。
- 输出以 `??` 开头 → 文件未被 git 跟踪：告诉用户「请先 `git add {notes_path}
  && git commit -m "..."` 建立基线」，**停止**。
- 其他输出（` M` / `M ` / `MM` / `A ` 等）→ 有未提交改动：告诉用户
  「{notes_path} 有未提交改动，请先提交或处理后再运行本 skill」，**停止**。

#### 1. 刷新单词本
```bash
uv run python .claude/skills/organize-words/export_words.py
```
先检查 `words.txt`（与脚本同在 skill 目录内）的状态，若它刚刷新过且本次无新增，跳过这个步骤。
（脚本会打开浏览器，约 1–2 分钟；若登录失效请让用户在弹出的浏览器里登录。）

#### 2. 准备待整理数据
```bash
uv run python .claude/skills/organize-words/prepare.py
```
输出**单行紧凑 JSON**（已刻意压缩体积，不要再格式化或原样回显）；关键字段：`words`
（`word` + 已精简的 `definition`）、`existing_groups`（现有分组 `num/num_cn/members`，
用于判断新词能否并入）、`next_group_number_cn`（起始组号）、`to_organize_count`、`date`、
`notes_path` / `draft_path`（与 config 一致，供阶段二复核）。

**若 `to_organize_count == 0`：没有新词，向用户说明后结束，不写任何文件。**

#### 3. 规划分组
按**规则 4** 的相关性门槛筛选，**宁可少建组**。对每个新词判断：
- 与某个 `existing_groups` 的组是**真同族**（同词根派生/屈折）？是 → **B 类（并入现有组）**。
  仅仅近义**不算**，不要并入。
- 否则能否与本批其他新词组成 **≥3 词**、且满足规则 4 三种关系之一的组？能 → **A 类（新增组）**。
- 都不满足 → **不成组**，也绝不补充词表外的词。留待下次运行（该词会再次出现）。

**自检**：逐组问「能否用一句话说清共同点，且不是『都属于某领域』？」。说不清就删掉。
最终组数偏少是正常的；若列出几十个组，说明门槛松了。

#### 4. 写草稿文件
把全部方案写入 `{draft_path}`（在 skill 目录内，已被 skill 自带的 `.gitignore` 忽略，
用完即删），**只列词族成员与一句理由**，不写释义/例句。格式：

~~~markdown
# 词块整理草稿（{date}）

待整理 {N} 个新词。请审阅后告诉我保留哪些（例如「保留 A1、A3、B1，跳过 A2」，也可要求修改某项）。**确认前不会改动 {notes_path}；确认后我会为选中项补全释义与例句再写入。**

> A 类 = 新增词块（≥3 词，选中后按顺序从 {next_group_number_cn} 起连续编号）；B 类 = 并入现有组（不占新编号）。只列强相关组；未成组的词不列出，下次运行仍会出现。

## A. 新增词块

### A1. confess / concede / acknowledge
> 理由：都表「承认」，互为近义说法。

### A2. singular / plural / dual
> 理由：语法中「数」的三种并列取值。

## B. 并入现有词块

### B1. precede → 组「五、precedent / precedence / unprecedented」
> 理由：precede 是 precedent / precedence 的同根动词。
~~~

要点：
- 草稿**只列成员 + 一句理由**，**不写**释义、例句、`#en`/`###` 等卡片正文——那些在阶段二
  确认后才生成。
- A 类每项 **≥3 词**，用临时编号（A1→`{next_cn}`、A2→`{next_cn+1}`…，最终按选中项顺序重排）；
  B 类引用现有组号与成员。
- 不成组的词直接省略，不在草稿里列出。
- **草稿短是正常的、也是期望的**：只保留满足规则 4 的组。

写完向用户简述：A 项新增组、B 项并入各有哪些；未成组词数一句话带过即可（**不追求覆盖率**）。
提示用户审阅 `{draft_path}` 并回复筛选。**然后停下等待用户回复，不要进入阶段二。**

### 阶段二：应用用户筛选

#### 5. 为选中项生成正文并写入
解析用户保留的 A/B 编号。先为每个选中项**生成完整卡片正文**（释义 + 每词 2 例句，按规则 8/9），
再写入文件。
- 全部跳过 → 报告无改动，删除草稿，结束。
- **B 类（并入现有组）**，逐项用 Edit：
  1. 先 Read 该组所在区域，拿到确切文本（最后一个例句行 + 紧随其后的 `<!--SR:...-->`）。
  2. 更新标题：`## {cn}、{原成员}` → `## {cn}、{原成员} / {新词}`。
  3. 插入新小节：以「该组最后一个例句行 + SR 行」为唯一锚点，
     `old_string` = `{最后例句}\n<!--SR:...-->`，
     `new_string` = `{最后例句}\n\n### {k}. {新词}\n- **释义**：...\n- **例句**：\n  - ...\n  - ...\n<!--SR:...-->`。
     `k` = 该组现有 `###` 小节数 + 1。**SR 行原样保留在末尾。**
- **A 类（新增组）**：按选中顺序从 `next_group_number_cn` 起连续编号（重排草稿里的临时编号）。
  用 Edit 追加——Read 文件尾部，取一个**唯一**锚点（如最后 1–2 行；`---` 不唯一，多取几行保证唯一），
  `old_string` = `{尾部锚点}`，`new_string` = `{尾部锚点}\n\n{新组块}`。每个新组块为
  `#en\n## {cn}、{成员}\n?\n` + 各词 `### N. word` + 释义 + 2 例句，组以 `---` 结尾，组间空一行。

> 全程只用 **Edit** 做定点修改，**不要用 Write 整文件覆盖**，以免误伤已有 SR 标记。

#### 6. 核对与收尾
```bash
git diff --stat -- {notes_path}
git status --porcelain -- {notes_path}
```
向用户报告：新增了哪些组、并入哪几个现有组、共涉及多少词；列出 `definition` 为空的词请复核。
删除 `{draft_path}`。建议用户审阅 diff 后 `git commit`。

## 补充说明

- 修改现有组时务必只插入、不删改已有小节与 SR 标记。
- 短语（如 `aside from`、`in charge of`）作为整体单元参与分组；但**不要仅因「都是短语」就建组**。
- 找不到 ≥3 词强相关归属的词（含多数短语、专有名词）不强行成组，留待下次；未成组的词
  下次运行会再次出现在 `words` 里，这是**预期行为，不是遗漏**，不必为此放宽门槛。
- 只有需要比 `definition` 更全的义项时，才去 `words.csv` 单查该词的长释义；**不要**整表读取。
- `prepare.py` 的输出体积是刻意控制的：原始长释义全量 dump 约 90KB，精简 + 紧凑后约 37KB，
  每次运行都会重新读一遍，所以别再往 payload 里加回全量释义或 `indent`。
- 若待整理词超过 40 个，草稿可分批生成（每批若干项写入草稿），避免单次输出过长。
- 环境为 Windows + Git Bash；`uv run python` 已配清华镜像，无需额外设置。
